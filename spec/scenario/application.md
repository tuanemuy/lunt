# 申請の共通の進み方

承認を必要とするすべての申請に共通する、申請者の確認・再提出・取り下げ・再申請と、承認者の承認・否認・差し戻しの流れを定める。

## 共通の規則

- 対象の申請は、店舗の新規登録、管理者のいない店舗の情報修正と休業・閉店、店舗の管理権限取得、地域所属、地域からの離脱、イベント参加、管理者のいない店舗の掲載、その掲載の修正の8種（P-70）。申請の内容、承認者、承認で反映される内容は、各カテゴリーのシナリオが定める
- 取り下げの申立てと、情報の誤り・閉店の連絡は申請ではなく、この進み方を適用しない（P-79）。`moderation.md` が定める
- 申請の状態は 確認中・差し戻し・承認・否認・取り下げ・失効（P-80）。提出した申請は確認中になる。承認・否認・取り下げ・失効の申請は、それ以上状態が変わらない
- すべての申請は、申請の内容に加えて、承認者への補足（自由記述）を持てる。補足は任意で、承認者が申請の内容とともに確認する
- 申請の提出と、申請に対するすべての操作にログインが必要（B-18）
- 個人として行った申請は、申請した利用者だけが扱う。店舗管理者として行った申請（地域所属、地域からの離脱、イベント参加）は、その店舗のすべての店舗管理者が扱う（P-76）
- 承認者は申請の種類で決まる。店舗の登録・情報修正・管理権限・掲載・掲載の修正はサービス運営者、地域所属と離脱はその地域の地域運営者、イベント参加はそのイベントのイベント運営者。運営者が不在の地域・イベントではサービス運営者が承認者になる（P-70、R-11、E-09）
- 承認者は自分の申請も承認できる（P-04）
- サービス運営者が行う代行（APP-08）の入口と、サービス運営者でない利用者がたどり着いたときの扱いは、`index.md` の「共通の規則 > サービス運営者の操作」が定める
- 同じ申請者が、同じ種類・同じ対象で確認中または差し戻しの申請を持つ間は、重ねて申請できない。店舗管理者として行う申請では、店舗を1人の申請者として数える（P-74）。別の申請者による同じ対象への申請は、それぞれ独立して確認される（P-75）
- 確認中・差し戻しの申請は、申請の前提が成り立たなくなると失効する。承認も同じ前提を確かめ、前提を欠く申請は承認できない。前提は `index.md` の「共通の規則 > 申請の前提」が定める（P-77、I-19）
- 否認・取り下げ・失効で終わった申請は、添えた写真を手放す。終わった申請の内容の表示は写真を含まない
- 申請の対象が運営による非公開、または店舗の非公開になっても、確認中・差し戻しの申請は失効しない。承認者が判断する
- 登録申請に併せた管理権限の申請は、登録申請とは別の申請として状態を持つ（M-45）
- 申請者には差し戻し・承認・否認・失効が、承認者には新しい申請・再提出・取り下げが通知される（P-91、P-92）。店舗管理者として行った申請の申請者宛ての通知は、その時点のその店舗のすべての店舗管理者に届く（P-76）。通知の確認は ACC-03

## APP-01 自分の申請の確認状況と結果を確認する

- 利用者: 利用者
- 契約: M-05、R-09、E-07、P-80、P-89、P-91、B-22、AC-21

### 流れ

1. 利用者は自分の申請の一覧を開く。申請についての通知からは、その申請を直接開く
2. 一覧で、申請ごとに種類、対象、状態を見る
3. 申請を選び、申請した内容と状態を見る。否認・取り下げ・失効の申請の内容は、写真を含まない
4. 状態に応じて次を確認し、次の操作へ進む
   - 確認中: 承認者の判断を待っていること。取り下げられる（APP-03）
   - 差し戻し: 承認者が求める追加の確認。修正して再提出する（APP-02）か、取り下げる（APP-03）
   - 承認: 反映された内容。反映先の店舗・掲載・地域・イベントを開ける。管理権限の承認では店舗の管理へ進む（SHP-05）
   - 否認: 否認の理由。再申請できる（APP-04）
   - 取り下げ: 自分が取り下げたこと。再申請できる（APP-04）
   - 失効: 失効した事情（APP-05）
5. 登録申請に管理権限の申請を併せた場合は、2つの申請の状態をそれぞれ見る

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| リソース不在 | 申請を1件も出していない | 申請がないことが示される。申請は各カテゴリーの入口から始める |
| リソース不在 | 承認で反映された対象が、その後に非公開・削除で閲覧できない | 申請の結果は確認できる。対象を開くと閲覧できないことが示される |
| 権限不足 | 他の利用者の申請に直接たどり着いた | 閲覧できないことが示される。自分の申請の一覧へ戻る |

## APP-02 差し戻された申請を修正して再提出する

- 利用者: 利用者
- 契約: P-72、P-71、P-92、M-05、M-40、B-22、AC-21、AC-43
- 前提: 申請が差し戻しの状態にある

### 流れ

1. 利用者は差し戻しの通知、または自分の申請の一覧から申請を開く
2. 承認者が求める追加の確認を読む
3. 申請の内容と、承認者への補足を修正する。入力できる内容は、その申請を定めるシナリオと同じ。地域所属・地域からの離脱のように内容が対象の指定だけの申請は、補足で追加の確認に答える。写真を新たに添えるときは、登録のたびに同意を確認する
4. 内容を確かめて再提出する
5. 申請は確認中に戻り、承認者に再提出が通知される

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 入力エラー | 修正した内容が、その申請の必須の内容を欠いている | 欠けている内容が示される。直して再提出する |
| 権限不足 | その申請を扱えない利用者が開いた | 操作できないことが示される |
| 操作の取り消し | 再提出せずに修正をやめた | 申請は差し戻しのまま変わらない。後から修正をやり直すか、取り下げる（APP-03） |
| 契約（P-77） | 修正している間に申請が失効した | 再提出できず、失効が示される。APP-05 へ進む |
| 契約（P-72） | 再提出した後で、修正をやり直したい | 確認中の申請は修正できない。取り下げて（APP-03）、再申請する（APP-04） |

## APP-03 申請を取り下げる

- 利用者: 利用者
- 契約: P-73、P-92、P-77、M-45
- 前提: 申請が確認中または差し戻しの状態にある

### 流れ

1. 利用者は自分の申請の一覧から申請を開く
2. 取り下げを選ぶ。取り下げた申請は元に戻せないことが示される
3. 取り下げを確定する
4. 申請は取り下げになり、承認者に通知される。申請の内容は反映されず、添えた写真は手放される
5. 管理権限の申請を併せた登録申請を取り下げると、併せた管理権限の申請は失効する（P-77c）。併せた管理権限の申請だけを取り下げると、登録申請は確認中のまま残る

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 権限不足 | その申請を扱えない利用者が開いた | 操作できないことが示される |
| 操作の取り消し | 確定の前にやめた | 申請は変わらない |
| 操作の取り消し | 取り下げた後で、申請を続けたい | 取り下げは元に戻せない。同じ対象に再申請する（APP-04） |
| 契約（P-71、P-77） | 取り下げる前に、承認者が承認・否認した、または申請が失効した | 取り下げできず、現在の状態が示される。結果を確認する（APP-01） |

## APP-04 否認・取り下げ・失効の後に再申請する

- 利用者: 利用者
- 契約: P-74、B-22、AC-21
- 前提: 同じ対象への申請が否認・取り下げ・失効のいずれかの状態にある

### 流れ

1. 利用者は自分の申請の一覧から、否認・取り下げ・失効の申請を開く
2. 否認の申請では否認の理由を、失効の申請では成り立たなくなった前提を確認する
3. その申請から再申請を始める。前の申請の内容と補足から写真を除いたものが入った状態で、入力が始まる
4. 内容を直して提出する。入力できる内容は、その申請を定めるシナリオと同じ。写真を添える申請では、写真を登録し直す。登録のたびに同意を確認する（`index.md` の「共通の規則 > 写真の登録と同意」）
5. 新しい申請が確認中になり、承認者に通知される。前の申請は否認・取り下げ・失効のまま残る

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 入力エラー | 必須の内容を欠いている。写真が必須の申請（掲載の申請）で、写真を登録し直していない場合を含む | 各申請のシナリオの入力エラーに従う |
| リソース不在 | 対象の店舗・掲載・地域・イベントが閲覧できない | 閲覧できないことが示され、再申請を始められない |
| 契約（P-74） | 同じ種類・同じ対象で、確認中または差し戻しの自分の申請がすでにある | 重ねて申請できないことが示される。その申請の結果を待つか、修正して再提出する（APP-02） |
| 契約（P-77） | 再申請する申請の前提が成り立っていない（管理者のいない店舗に店舗管理者が就いた、参加を再申請するイベントが終了または中止している、など） | 再申請できないことと、成り立っていない前提が示される。前提が成り立つようになった後に再申請する。管理者のいる店舗の情報の誤り・閉店は連絡できる（MOD-04） |

## APP-05 申請の失効を知る

- 利用者: 利用者
- 契約: P-77、P-91、P-34、M-45、B-22、I-02、I-08、I-19、AC-66
- 前提: 確認中または差し戻しの申請の前提が成り立たなくなった

### 流れ

1. 申請が失効すると、申請者に失効が通知される。店舗管理者として行った申請では、その店舗のすべての店舗管理者に通知される。店舗管理者が不在になって失効した申請（P-77b）では、店舗管理者がいないため、通知はサービス運営者に届く
2. 利用者は通知、または自分の申請の一覧から申請を開く
3. 申請が失効したことと、成り立たなくなった前提を確認する。申請の内容は反映されない
4. 成り立たなくなった前提に応じて、次の操作へ進む。前提は `index.md` の「共通の規則 > 申請の前提」が定め、次の表はその例（P-77、I-19）

| 成り立たなくなった前提 | 例 | 利用者の次の操作 |
| --- | --- | --- |
| その店舗に店舗管理者がいない | 個人が管理者のいない店舗に行った申請の確認中に、店舗管理者が就いた（P-77a） | 申請はできない。情報の誤り・閉店は連絡できる（MOD-04） |
| その店舗に店舗管理者がいる | 店舗管理者として行った申請の確認中に、最後の店舗管理者が権限を手放した、解除された、または退会した（P-77b、P-34、I-02） | 失効の通知はサービス運営者に届く。最後の店舗管理者本人は、権限を手放す確認（MEM-04）または退会の確認（ACC-04）で、申請が失効することを示されている。管理者のいない店舗の所属・離脱は、利用者として申請できる（REG-03）。再び店舗管理者になるには管理権限を申請する（SHP-04） |
| 併せた登録申請が否認・取り下げになっていない | 登録申請が否認または取り下げになった（P-77c） | 登録申請の否認の理由を確認する。登録を再申請するときに管理権限の申請を併せる（SHP-03）。既存の店舗と重複していたなら、その店舗の管理権限を申請する（SHP-04） |
| 申請者がその店舗の店舗管理者でない | 管理権限の申請者が、招待の承諾でその店舗の店舗管理者になった（P-77d） | すでに店舗管理者である。店舗の管理へ進む（SHP-05） |
| 対象の掲載がある | 掲載の修正の申請の確認中に、掲載が削除された（P-77e） | 修正する対象がない。店舗に管理者がいなければ、新しい掲載を申請できる（LST-12） |
| その店舗とその地域の所属がまだない | 別の申請の承認で、所属がすでに成立した（P-77f） | 所属は成立している。操作は要らない |
| その所属がある | 除外、または別の離脱の申請の承認で、所属が解除された（P-77f） | 所属は解除されている。操作は要らない |
| イベントが開催前または開催中で、その店舗の参加がまだない | イベントが終了または中止した（P-77g） | 失効した申請は戻らない。イベントが開催前・開催中に戻った後に、参加を再申請する（APP-04、EVT-01） |

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 操作の取り消し | 失効した申請を元に戻したい | 失効は元に戻せない。前提が再び成り立った後に再申請する（APP-04） |

## APP-06 店舗管理者として行った申請を、同じ店舗の別の店舗管理者が扱う

- 利用者: 店舗管理者
- 契約: P-76、M-08、P-72、P-73、AC-66
- 前提: 同じ店舗の店舗管理者が、地域所属・地域からの離脱・イベント参加を申請している

### 流れ

1. 店舗管理者は、管理する店舗の申請を開く。対応が必要な申請は店舗の状況（SHP-05）から把握する。申請の差し戻し・承認・否認・失効は、申請した店舗管理者に限らず、その店舗のすべての店舗管理者に通知される
2. 別の店舗管理者が出した申請を含め、その店舗の申請の種類、対象、状態、内容を見る
3. 差し戻しの申請を修正して再提出する（APP-02）。確認中・差し戻しの申請を取り下げる（APP-03）。否認・取り下げ・失効の後に再申請する（APP-04）
4. 申請した店舗管理者が権限を手放すか退会しても、他の店舗管理者がいる間は申請が続き、残る店舗管理者が同じように扱う

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 権限不足 | 権限を手放した、または解除された利用者が、自分の出した申請を開いた | 操作できないことが示される。店舗管理者として行った申請は、その店舗の店舗管理者だけが扱う |
| 契約（P-76） | 別の店舗管理者が先に同じ申請を再提出した、または取り下げた | 操作は行われず、申請の現在の状態が示される。状態を確かめて、必要な操作があれば行う |
| 契約（P-77b） | 最後の店舗管理者が権限を手放す、解除される、または退会する | 店舗管理者として行った確認中・差し戻し中の申請はすべて失効し、失効の通知はサービス運営者に届く（APP-05）。権限を手放す確認（MEM-04）と退会の確認（ACC-04）で、失効することが示される |

## APP-07 確認中の申請を承認・否認・差し戻しする

- 利用者: 承認者（サービス運営者、地域運営者、イベント運営者）
- 契約: P-71、P-91、P-92、P-75、P-04、B-22、M-05、O-04
- 前提: 自分が承認者である申請が確認中の状態にある

### 流れ

1. 承認者は新しい申請または再提出の通知、もしくは対応が必要な申請の一覧から申請を開く
2. 申請者、対象、申請の内容を確認する。確認する内容と、承認で反映される内容は、各カテゴリーの判断のシナリオが定める（SHP-09、SHP-10、SHP-11、LST-14、REG-09、EVT-08）
3. 次のいずれかを行う
   - 承認する。申請の内容が反映され、申請は承認になる
   - 理由を添えて否認する。申請は否認になり、内容は反映されない
   - 追加で必要な確認を添えて差し戻す。申請は差し戻しになり、申請者の再提出を待つ
4. 申請者に結果が通知される。否認の理由と、追加で必要な確認は、申請者が申請の中で確認できる
5. 同じ対象への複数の申請は、1件ずつ判断する。自分が出した申請も同じ流れで判断できる
6. 申請の対象が運営による非公開、または店舗の非公開になっていても、申請は確認中のまま残り、同じ流れで判断する

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 入力エラー | 理由を添えずに否認しようとした、または追加で必要な確認を添えずに差し戻そうとした | 否認・差し戻しできないことが示される。理由または必要な確認を書く |
| 権限不足 | その申請の承認者でない利用者が申請にたどり着いた | 操作できないことが示される |
| リソース不在 | 判断する前に、申請者が申請を取り下げた、または申請が失効した | 判断できず、現在の状態が示される。対応は要らない |
| 契約（P-77） | 承認しようとした時点で、申請の前提が成り立っていない | 承認できないことと、成り立っていない前提が示される。申請は失効する。対応は要らない |
| 契約（P-71） | 同じ申請の別の承認者（同じ地域・イベントの別の運営者、別のサービス運営者、代行するサービス運営者）が先に判断した | 先の判断が有効になる。判断は行われず、申請の現在の状態が示される。結果を確かめる。対応は要らない |
| 操作の取り消し | 確定の前にやめた | 申請は確認中のまま変わらない |
| 操作の取り消し | 確定した承認・否認・差し戻しを変えたい | 判断は変えられない。承認で反映した内容は反映先の操作（情報の更新、除外、権限の解除など）で直す。否認・差し戻しは、申請者の再申請・再提出を受けて判断する |

## APP-08 運営者が確認しない申請を代行して承認・否認する

- 利用者: サービス運営者
- 契約: P-78、B-52、R-11、E-09、O-11、O-12、P-97、X-04、AC-67
- 前提: 運営者のいる地域への所属・離脱の申請、または運営者のいるイベントへの参加の申請が、確認中のまま一定の期間を過ぎている。期間は、申請が確認中になった時点（提出または再提出）から数える。期間の値は設定が定める

### 流れ

1. 期間を過ぎた申請があると、サービス運営者に通知される
2. サービス運営者は通知、または対応が必要な申請の一覧（OPE-01）から申請を開く
3. 申請者、対象の店舗、対象の地域またはイベント、申請の内容を確認する
4. 承認するか、理由を添えて否認する。代行では差し戻せない。承認で反映される内容は、運営者が承認した場合と同じ（REG-09、EVT-08）
5. 申請者に結果が通知される。地域運営者・イベント運営者は、申請の結果を申請の確認（REG-08、EVT-07）で把握する

運営者が不在の地域・イベントの申請は、サービス運営者が承認者として APP-07 の流れで判断する。

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 入力エラー | 理由を添えずに否認しようとした | 否認できないことが示される。理由を書く |
| 権限不足 | 運営者がいて、期間を過ぎていない申請にたどり着いた | 代行できないことが示される。運営者の判断を待つ |
| リソース不在 | 代行する前に、運営者が判断した、申請者が取り下げた、または申請が失効した | 判断できず、現在の状態が示される。対応は要らない |
| 契約（P-71） | 追加の確認が必要な申請を代行する | 代行では差し戻せない。承認するか、理由を添えて否認する。否認された申請者は再申請できる（APP-04） |
| 操作の取り消し | 確定の前にやめた | 申請は確認中のまま変わらない。運営者も引き続き判断できる |
| 操作の取り消し | 確定した承認・否認を変えたい | APP-07 と同じ |
