## 読むもの

1. `spec/review/contract.md` — 契約。とくに D-01〜D-09（画面構成の参考）、P-30、P-32、P-87、P-88、解釈 I-01〜I-17
2. `spec/scenario/index.md` と `spec/scenario/*.md` — 上流。pages はすべてのシナリオを実現する画面の構成を述べる
3. `spec/review/decisions-scenario.md` — シナリオ層で決めた事項（シナリオに反映済み）
4. 必要に応じて `spec/design-appendix.md`（APX）の 4〜7

## 層の決まり

| 層 | 上流 | 決め切る | 書かない |
| --- | --- | --- | --- |
| `spec/pages/` | scenario | 画面・目的・機能・状態と遷移のきっかけ | 条件の組み合わせを展開した個別ケース、データ項目の型・制約、メッセージの文面 |

- 既に書かれた原則・共通規則から導出できる個別ケースは、規則がある時点で定義済み。共通規則は `spec/pages/index.md` に1回だけ書く
- 状態遷移の詳細な事前条件・事後条件、エラーメッセージの文面、色・寸法・書体・レイアウトの細目は書かない
- 各画面の目的が一文で言え、2つの画面が同じ役割を負わない。利用者の目的が不要なステップなしに達成できる
- すべてのシナリオ ID が、どれかの画面の機能に辿れる。上流のシナリオにない機能を足さない
- 現在形で書く。経緯・代替案・検討の過程は書かない
- シナリオから決まらない判断が必要になったら、補完せず返答の「未決の問い」に挙げる

## 構成

- `spec/pages/index.md` — 画面の一覧（ID・画面名・目的の一文・実現するシナリオ ID）を画面群ごとの表で持つ。加えて、ナビゲーション（閲覧側の下部ナビゲーション D-05、店舗側の管理ナビゲーション D-07、地域・イベント・編集・運営の管理の入口）、全画面に共通の状態と規則（読み込み中・通信エラー・ログインが必要・権限なし・閲覧できない対象・競合・写真の登録と同意・申請の状態の示し方・公開中の対象の状態の示し方 など）、画面設計で定める値（フィードの挿入間隔と巡回の順 P-30、関連情報の選び方 P-32、地図の再検索とピンの集約 D-09）を持つ
- `spec/pages/${group}.md` — 画面群ごとの詳細。各画面は次の形

```markdown
## {画面 ID} {画面名}

- 目的: {この画面が存在する理由を一文で}
- シナリオ: {実現するシナリオ ID}
- 入口: {どの画面・通知・リンクから来るか}

### 機能

- {この画面で行えること}

### 状態

| 状態 | 内容 | 遷移のきっかけ |
| --- | --- | --- |
```

画面群と ID の接頭辞は一覧の設計者が決める（例: 閲覧 V-、アカウント A-、店舗管理 S-、地域運営 R-、イベント運営 E-、サービス運営 O-、編集 T-）。同じ画面の状態違い（未保存、検索0件、イベント未開催、読み込み、通信エラー、位置情報未許可、保存後の状態 など）は、別の画面にせず、画面の状態として書く。

## 返答

成果物はファイルに書き、返答は要約だけにする（書いたファイル、画面数、未決の問い、上流の過不足。散文は5行以内）。ファイルの読み取りは Read / Grep ツールを使う。担当外のファイルは変更しない。

## 詳細の担当への追加の指示

- `spec/pages/index.md` が正。画面 ID・画面名・目的・シナリオ・入口・役割の負い先・共通の状態（CS）・共通の機能（CF）・状態の示し方・画面設計で定める値は一覧が定めている。詳細ファイルは一覧の内容を繰り返さず、CS・CF は ID で参照する
- 各画面の「機能」は、その画面が実現するシナリオの流れと異常系を読んで書く。シナリオの異常系のうち、共通の状態（CS）で表せるものは ID の参照で済ませ、その画面に固有のものだけを状態の表に書く
- 一覧に誤り・不足（割り当てのない操作、役割の重なり、入口の欠落）を見つけたら、一覧は直さず返答で伝える
- すべての申請は承認者への補足（自由記述）を持てる（`spec/review/decisions-scenario.md` の A-0）
