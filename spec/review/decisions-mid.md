# 中間の読みを受けた決定

`spec/review/read-mid.md` の反例への決定。spec には現在形の事実として書く（経緯・「変更した」などは書かない）。`decisions-scenario.md` と食い違う点は、こちらが正。

## 体験（scenario / pages）

- M-1 所在地のエリア: 所在地は、郵便番号または都道府県・市区町村・町域の階層から町域を選んで決める。町域に対応しない郵便番号（事業所固有の郵便番号を含む）は町域の候補が出ず、町域を選び直す（入力エラー）。店舗（SHP-03・06・08・12・13）とイベントの開催場所（EVT-04・12）、地域の所在地（REG-06・12）に共通
- M-2 招待: 対象が管理者不在になっても、承諾前の招待は有効のまま残る。引き継ぎは「後任を招待する → 自分の権限を手放す」で終わり、後任は後から承諾して管理者になる（B-29、AC-28）。管理者不在の間、承諾前の招待の取り消しはサービス運営者が行う（代行）。管理者のいなかった店舗の管理権限は、申請の承認のほか、この招待の承諾でも得られる。「管理者不在で招待が無効になる」旨の表示・異常系・確認はすべてなくす（`decisions-scenario.md` の A-3・K-4 は無効）
- M-3 終了・中止したイベント: 参加内容の変更・取りやめ・直接の追加・除外は、開催の状態にかかわらず行える。中止と中止の取り消しも、開催の状態にかかわらず行える。参加の申請だけは、開催前・開催中のイベントにしか出せない（M-5 の前提）（`decisions-scenario.md` の R-4 は無効）
- M-4 連絡の対応: 店舗管理者が確認の結果を伝えて連絡を対応済みにする操作はない。店舗管理者は確認の依頼を読み、必要なら店舗情報・掲載を更新する（MOD-06、SM-07 は依頼の内容を読んで SM-02・SM-03・SM-04 へ進む画面）。連絡を対応済みにするのはサービス運営者だけ（MOD-05）。サービス運営者は店舗の現在の情報を見て判断する（`decisions-scenario.md` の L-4 は無効）
- M-5 申請の前提: 申請の種類ごとに「前提」が1つ決まる。確認中・差し戻し中の申請は、前提が成り立たなくなると失効する。承認も同じ前提を確かめ、前提を欠く申請は承認できない（CS-08）。P-77 の a〜g はこの規則の例
  - 個人が管理者のいない店舗に行う申請（情報修正、掲載、掲載の修正、所属、離脱）: その店舗に店舗管理者がいない
  - 店舗管理者として行う申請（所属、離脱、参加）: その店舗に店舗管理者がいる
  - 掲載の修正: 対象の掲載がある（削除されていない）
  - 所属: その店舗とその地域の所属がまだない。離脱: その所属がある
  - 参加: イベントが開催前または開催中で、その店舗の参加がまだない
  - 管理権限: 申請者がその店舗の店舗管理者でない。登録申請に併せた管理権限の申請は、加えて、登録申請が否認・取り下げ・失効になっていない
  - 店舗の新規登録: 前提を持たない（失効しない）
  - 同じ店舗・同じ地域からの離脱を2人が申請し、一方が承認されると、他方は前提（所属がある）を失って失効する
- M-6 修正の申請の内容: 情報修正の申請と掲載の修正の申請は、変更した項目だけを持つ。承認は、その項目だけを対象の現在の内容に反映する。判断の画面（CM-01）は、変更する項目について、現在の値と申請の値を見比べて示す
- M-7 再申請: 否認・取り下げ・失効の申請から再申請を始めると、前の申請の内容と補足が入った状態で入力が始まる。新しい申請として提出され、前の申請はそのまま残る（`decisions-scenario.md` の C-3 の最後の文は無効）
- M-8 メールアドレスでのログイン: ログイン用のメールは、ワンタイムのリンクとワンタイムのコードの両方を載せる。メールアドレスを入力したブラウザでコードを入力すると、そのブラウザでログインが成立し、端末の保存の合流と元の操作への復帰がそのブラウザで起きる。リンクを開くと、開いたブラウザでログインが成立する。どちらも有効期間があり、一方を使うと他方も無効になる
- M-9 外部アカウント: 提供元が確認済みとしたメールアドレスだけを受け取る。確認済みのメールアドレスを受け取れなければログインは成立しない
- M-10 保存一覧の解除の取り消し: 保存一覧で解除した対象は、一覧を開き直すまで解除済みとして同じ行に残り、その行で保存し直せる。閲覧できない保存も同じ
- M-11 マップの初めの範囲: 選択エリアも現在地もない場合は、公開中の店舗が収まる範囲を、ピンをまとめて件数を示した状態で表示し、位置情報未許可であることを併せて示す。閲覧者は地図を動かして探せる
- M-12 表示範囲の規則（P-87、B-46）: 場面を2種に分け、規則はこの1か所（scenario は `spec/scenario/index.md` の共通の規則、pages は `spec/pages/index.md` の「公開中の対象の状態」）だけに書く。各シナリオ・各画面は、どちらの場面かだけを述べ、場面の列挙を繰り返さない
  - 発見の場面: 提供開始前・提供終了の掲載、閉店した店舗とその掲載、終了・中止したイベントを表示しない。フィード、絞り込みの結果、地図と地図の一覧、地域の一覧、地域内の一覧、イベントの一覧、地域詳細の店舗と掲載、掲載詳細の他の掲載、掲載・店舗・地域の詳細の関連するイベント
  - 参照の場面: 状態を区別して表示する。キーワード検索、既存店舗の確認、保存一覧、掲載詳細、店舗詳細（その店舗の掲載、地図を含む）、イベント詳細（参加店舗、添えた掲載、参加店舗の地図）、読みものからのリンク、入力の途中の対象の選択の候補
  - 休業中の店舗とその掲載、開催前のイベントは、どちらの場面でも状態を区別して表示する。非公開・公開の取り下げ・削除の対象と、非公開の店舗の掲載は、どちらの場面にも表示しない
- M-13 提供の設定: 掲載の提供の設定は「設定しない / 提供期間 / 開催日」のどれか1つを選ぶ排他的な選択。切り替えると、前の設定は持たない。「両方を設定して保存しようとした」異常系と「外してから設定する」手順はなくす
- M-14 運営による非公開の間の写真の削除: 運営による非公開の間に、申立てで最後の写真が削除されて公開条件を欠いた対象は、公開していない状態（掲載は一時非公開、地域・イベントは公開の取り下げ）になる。解除しても、写真を登録して公開し直すまで閲覧できない
- M-15 管理者のいない店舗の通知: 店舗管理者宛ての通知を、管理者不在のためにサービス運営者が受けた場合、通知は対象の運営（OM-03）を開く。地域・イベントの運営者が不在の場合の運営者宛ての通知も同じ
- M-16 未登録の場所を登録する入口: MY-01 は「店舗・スポットを登録する」入口を持ち、RQ-02（店舗を探す）を開く。店舗向け案内（RQ-01）を通らずに登録の申請へ進める
- M-17 `scenario/listing.md` と `scenario/moderation.md` の各シナリオの「契約」に、関連する AC の ID を足す（AC-10、AC-19、AC-24、AC-27、AC-30、AC-31、AC-38、AC-44、AC-46、AC-47、AC-48、AC-58、AC-59、AC-64、AC-65、AC-72、AC-77、AC-78、AC-79 など、契約の AC の関連要件から辿る）

## 技術設計（domains 以降。`spec/domains/index.md` に反映済みの内容を正とする）

- 催しのドメインの英語名は `Occasion`（ID は `OccasionId`）。ドメインイベントと名前が重ならない
- 写真: 写真を持つドメインは共有カーネルの `PhotoId`・`PhotoSet` だけを参照し、Media に依存しない。Media は共有カーネルの `PhotosReleased` ドメインイベントだけを消費する
- 申請の失効は前提の再評価（M-5）。日付で決まる状態の「最後に確かめた状態」は集約の外の記録が持つ
- 店名・住所の照合は Place のポートの1つの問い合わせ（非公開を含めるかは引数）
