# scenario 詳細の委譲ブリーフ

リポジトリは `/Users/hikaru/github.com/tuanemuy/lunt`。最初にルートの `AGENTS.md` を読む（このリポジトリの CLAUDE.md に当たる）。

## 読むもの

1. `spec/review/contract.md` — 契約。要求の台帳（分母）、範囲の外、解釈
2. `spec/scenario/index.md` — シナリオ一覧。担当カテゴリーの ID と操作名はここが正
3. 必要に応じて `spec/requirements.md`（REQ）、`spec/design-appendix.md`（APX）の該当節。契約の一行で足りないときに原文を確かめる

## 書くもの

担当カテゴリーの `spec/scenario/${category}.md`。担当外のファイルは変更しない。一覧に操作の過不足を見つけたら、ファイルは直さず返答で伝える。

## 層の決まり

| 層 | 上流 | 決め切る | 書かない |
| --- | --- | --- | --- |
| `spec/scenario/` | 契約 | 利用者の操作とフロー、異常系 | UI パターン（タブ・モーダル・ボタンの配置等） |

- 利用者の視点で、具体的なフローが分かるように書く
- 正常系に加え、契約が定める異常系と、4 観点（入力エラー・権限不足・リソース不在・操作の取り消し）の異常系を書く。異常系は「状況」と「利用者の次の操作」が決まるところまで書く。その操作で起こり得ない観点は書かない
- 契約にない要求を足さない。契約から決まらない判断が必要になったら、補完せず返答の「未決の問い」に挙げる
- 現在形で書く。経緯・代替案・旧仕様・検討の過程は書かない
- 画面構成（どの画面に何を置くか）は pages が決める。シナリオは「どこから始めて、何を見て、何をして、何が起きるか」まで
- ドメインの型・ポート・データ項目の制約は書かない

## 形式

```markdown
# {カテゴリー名}

{カテゴリーの一文の説明}

## {ID} {操作名}

- 利用者: {一覧の利用者}
- 契約: {辿り先の契約の番号。例: V-09、P-13、AC-03}
- 前提: {始めるときの状態。なければ省く}

### 流れ

1. {利用者の操作と、システムの応答を利用者から見える形で}

### 異常系

| 観点 | 状況 | 利用者の次の操作 |
| --- | --- | --- |
| 入力エラー / 権限不足 / リソース不在 / 操作の取り消し / 契約（番号） | ... | ... |
```

文章は簡潔に、断定で書く。同じカテゴリーの複数のシナリオに共通する規則は、カテゴリーの冒頭に「共通の規則」として1回だけ書き、各シナリオからは繰り返さない。

## カテゴリーをまたぐ決定

全カテゴリーで同じ前提にする。自分のカテゴリーに関係するものだけを、現在形の事実として書く。

- 用語は契約の語を使う。「店舗」は店舗・スポットを指す。申請の状態は 確認中・差し戻し・承認・否認・取り下げ・失効。掲載の公開状態は 下書き・公開・一時非公開・運営による非公開、提供状態は 提供開始前・提供中・提供終了。店舗は 公開・非公開 と 営業中・休業・閉店。地域・イベント・読みものは 下書き（未公開）・公開・公開の取り下げ、地域・イベントはそれとは別に 運営による非公開。イベントの開催は 開催前・開催中・終了・中止
- 日付で決まる状態（提供開始前・提供終了、開催前・開催中・終了）は日本時間の日付で自動で決まる
- ログインが必要な操作をログインせずに始めた利用者は、ログインへ案内され、ログイン後に元の操作へ戻る（B-18）
- 権限のない操作は入口が示されず、直接たどり着いても操作できないことが示される
- 非公開・公開の取り下げ・削除で閲覧できない対象を開くと、閲覧できないことが示され、他の探索へ進める（P-88、B-10、B-27）。存在しない対象も同じ扱い
- ログインしていない間の保存は端末のブラウザに残し、サーバーに送らない。ログインすると、端末の保存をアカウントの保存に合流する（V-41、V-52）
- 管理メンバーの招待はメールアドレス宛てに行う。招待された利用者が、そのメールアドレスのアカウントでログインして承諾すると管理者になる。管理者は承諾前の招待を取り消せる。招待に期限はない（B-28、B-32、P-98）
- 写真を登録する操作のたびに、写真の権利と Lunt での利用への同意を確認する（M-37、B-53）
- 通知はメールとサービス内の通知一覧の両方に届く。通知の出来事は契約 P-91〜P-100 が正（B-39）
- 承認者が行う承認・否認・差し戻しと、申請者が行う再提出・取り下げ・再申請の共通の流れは `application.md` が定める。各カテゴリーのシナリオは、申請の内容・承認者・承認で反映される内容と、そのカテゴリーに固有の異常系だけを書き、共通の流れは `application.md` の ID で参照する
- 管理権限の招待・辞任・解除の共通の流れは `membership.md` が定める
- 取り下げの申立てと情報の誤り・閉店の連絡は申請ではなく、`moderation.md` が定める

## 返答

成果物はファイルに書き、返答は要約だけにする。

- 書いたファイルとシナリオ数
- 未決の問い（契約から決まらなかった判断。なければ「なし」）
- 一覧の過不足（なければ「なし」）
- 散文は5行以内。ファイルの読み取りは Read / Grep ツールを使う
