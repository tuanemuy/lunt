# 独立した読み（scenario / pages 一覧 / domains 一覧）

読んだ範囲は `spec/scenario/`（index と13カテゴリー）、`spec/pages/index.md`、`spec/domains/index.md`。基準は `spec/review/criteria.md`、上流は `spec/review/contract.md`。未執筆の層（pages の画面群ごとのファイル、domains のドメインごとのファイル、usecases、flows、testcases）が無いことは反例にしていない。

## 条件1 要求を取りこぼしていない

### 1-1 事業所固有の郵便番号を持つ所在地のエリアが決まらない

- 引用（契約 P-12）: 「エリアは町域の郵便番号を単位とする。事業所固有の郵便番号は独立したエリアにしない。店舗・スポットのエリアは所在地から判断し」
- 落ちている場所
  - `scenario/shop.md` 共通の規則: 「店舗のエリアは所在地から決まる。利用者はエリアを入力しない（P-12）」。SHP-03・SHP-06・SHP-08・SHP-12 の異常系に、所在地の郵便番号が事業所固有である場合がない
  - `scenario/event.md` EVT-04 手順4: 「イベントのエリアは、開催場所の所在地から決まる」。同じ場合がない
  - `domains/index.md` 日付と位置: 「`Address` … 対象のエリアは `postalCode` で決まる」
- 反例の内容: 事業所固有の郵便番号を入力した店舗・イベントは、`postalCode` に対応するエリアがない。入力エラーの観点で、利用者の次の操作（町域の郵便番号に直すのか、受け付けて町域のエリアに寄せるのか）が決まっていない。絞り込み（V-09、V-47）に現れない店舗ができる

## 条件2 足しすぎていない

### 2-1 管理者不在で承諾前の招待が無効になる規則

- 引用（`scenario/membership.md` 共通の規則）: 「対象が管理者不在になると、承諾前の招待は無効になる」。同じ規則が MEM-02 手順6、MEM-03 異常系、MEM-04 手順2、MEM-05 手順3、`scenario/account.md` ACC-04 手順2・3 に展開されている
- 上流に引用元がない。同じ箇条書きが引く B-32 は「管理権限は期間の経過や利用状況で自動失効しない」で、招待の無効化を述べていない
- 契約 B-29「引き継ぎは後任を招待した後に手放す」、AC-28「管理者が後任を招待して自分の権限を手放せる」の手順（招待 → 手放す）を最後の管理者が行うと、この規則で招待が無効になり、引き継ぎが成立しない。MEM-04 は「後任が承諾して管理者の一覧に加わったことを確かめてから」に読み替えている

### 2-2 終了・中止したイベントでの操作の制限

- 引用（`scenario/event.md` 共通の規則）: 「終了・中止したイベントでは、参加の申請、店舗の直接の追加、参加内容の変更はできない」。EVT-02・EVT-10 の異常系は観点を「契約（共通の規則）」とし、契約の ID を引いていない
- 引用（EVT-11 異常系）: 「終了したイベントを中止にしようとした。中止にできないことが示される」。観点は同じく「契約（共通の規則）」
- 上流に引用元がない。契約が終了・中止に結びつけるのは参加申請の失効（P-77g）と表示範囲（P-87d）だけ。E-10「店舗管理者は承認なしで…添えた掲載・参加日を変更できる」、E-11、E-14 に開催の状態による制限はない。終了・中止したイベントの詳細は閲覧できる（V-43）ため、誤った参加日を直せない状態が残る

### 2-3 店舗管理者の報告で連絡が対応済みになる操作

- 引用（`scenario/moderation.md` MOD-06 手順5）: 「確認を終えたら、結果（情報を更新した、誤りはなかった）を選んで、確認を終えたことをサービス運営者に伝える。連絡は対応済みになる」。`pages/index.md` SM-07 がこの操作のための画面を持つ
- 上流に引用元がない。M-48・O-24・B-59 が定めるのは、サービス運営者の確認の依頼と、対応がない場合の権限の解除と更新。I-03 は「『店舗管理者が対応しない』の判断はサービス運営者が行い」とする。店舗管理者が「誤りはなかった」を選ぶだけで、サービス運営者の判断なしに連絡が閉じる

## 条件3 Issue をまたぐ決定が決まりきっている

### 3-1 離脱申請の対象の所属が、別の離脱申請の承認で解除された場合の遷移がない

- 引用（`scenario/region.md` REG-09 手順3）: 「同じ店舗とこの地域への、他の確認中・差し戻し中の所属申請は失効する」。手順4（離脱の承認）には、他の離脱申請の扱いがない
- 引用（REG-03 異常系）: 「別の利用者の申請があっても申請できる」
- 状態: 管理者のいない店舗について、2人の利用者が同じ地域からの離脱を申請し、一方が承認された後の、もう一方の確認中の離脱申請
- 欠けている遷移・主体: 失効（または判断不能）への遷移と、その実行主体。P-77f と REG-10 手順5は除外による解除だけを失効にする。残った離脱申請は確認中のまま残り、その後に同じ店舗の所属が再び成立すると、古い離脱申請を承認して新しい所属を解除できる
- 依存する2か所: 離脱を承認するユースケース（所属がない申請の承認の結果）と、失効の消費者（`domains/index.md` の「Region のイベント型 ← Application」）。画面では CM-01 の CS-08

### 3-2 写真の生成・参照・削除が揃っていない

- 引用（`domains/index.md` 写真の持ち主）: 「写真（`PhotoAsset`）は、ただ1つの持ち主（対象の集約、または申請）を持つ。掲載の複製と、申請の承認による反映は、持ち主を変えるか、写真を複製して新しい `PhotoAsset` を作る。持ち主から外された写真と、持ち主が削除された写真は、Media が削除する」
- 引用（同 依存方向）: 「Place, Listing, Region, Event, Article のイベント型 ← Media（写真の削除の消費者）」
- 答えが決まっていない問い
  - 申請の承認で写真の持ち主を変えるのか、複製するのか（「変えるか、…複製して」のまま）。依存する2か所: Media のポートの契約（持ち主の付け替えか複製か）と、承認のユースケース（SHP-09・SHP-11・LST-14）。複製なら、承認済みの申請が持つ元の写真の削除も要る
  - 否認・取り下げ・失効で終わった申請が持ち主の写真を、誰がいつ削除するか。申請は削除されず、Media が消費するイベント型に Application がない。状態は「終端に達した申請が持つ写真」、欠けているのは削除の遷移と実行主体
  - 保存・提出の前に登録された写真の扱い。`pages/index.md` CF-01 は「登録・並び順・削除は、画面の保存または提出で反映する」とし、同意は「登録の操作のたび」に確かめる。保存せずに離れた（CS-11）写真は持ち主を持たず、「ただ1つの持ち主を持つ」に当てはまらない。削除の主体がない

### 3-3 店舗管理者が伝えた確認の結果に、受け取る経路がない

- 引用（`scenario/moderation.md` MOD-05 手順5）: 「サービス運営者は、伝えられた結果（情報を更新した、誤りはなかった）を連絡で確認できる」
- 引用（`scenario/operation.md` OPE-01 手順5）: 「対応を終えた申立て・連絡は、対応が必要なものから外れる」。`pages/index.md` 申請の状態: 「OM-01 は、対応が必要なものだけを示す」。OM-05 の入口は「OM-01、連絡の通知」
- 引用（`scenario/moderation.md` 共通の規則）: 「通知の出来事は P-91〜P-100 が正」。P-97 に、店舗管理者の報告の通知はない
- 状態: 店舗管理者の報告で対応済みになった連絡。欠けているのは、伝えられた結果の消費者へ届く経路。報告と同時に連絡が OM-01 から外れ、通知もないため、サービス運営者は結果を開く入口を持たない
- 依存する2か所: MOD-06 のユースケース（報告で閉じるか、報告済みとして残すか）と、OM-01・OM-05 の一覧の範囲

### 3-4 運営による非公開の間に、申立てで最後の写真が削除された対象の公開状態

- 引用（`domains/index.md` 運営による非公開）: 「公開状態に重なる別の状態で、公開状態を書き換えない」「運営による非公開の間、対象は閲覧できず、公開状態を変える操作は `BusinessRuleError` になる」

- 答えが決まっていない問い: 運営による非公開かつ `published` の対象から最後の写真を削除したとき、`unpublished` になるのか、`published` のままか。前者は「書き換えない」に、後者は解除後に写真のない対象が公開される点で M-49・B-61 に反する
- 依存する2か所: Listing・Region・Event の集約の振る舞いと、MOD-02 のユースケースのテストケースの期待結果（解除後の公開状態）

### 3-5 修正の申請の内容が、変更した項目だけか、全項目の写しか

- 引用（`scenario/shop.md` SHP-08 手順2）: 「現在の店舗情報を見て、修正する内容を入力する」。異常系: 「現在の店舗情報から何も変えていない。提出できない」
- 引用（SHP-11 異常系）: 「承認は申請の内容の全体を反映する」「先の承認で店舗情報が変わると、残りの申請は変わった後の店舗情報と見比べて判断する」。SHP-13 異常系: 「更新しても申請は確認中のまま残る」。`scenario/listing.md` LST-14 手順7も同じ

## 条件5 利用者の目的が迂回なく達成でき、画面の役割が重ならない

### 5-1 ログイン用のリンクを別のブラウザで開くと、保存の引き継ぎと元の操作への復帰が成立しない

- 引用（`scenario/account.md` ACC-01 手順3・4）: 「ワンタイムのリンクを載せたログイン用のメールが届く」「メールのリンクを開くと、リンクを開いたブラウザでログインが成立する」
- 引用（`scenario/keep.md` KEP-04 異常系）: 「ログイン用のメールのリンクを、保存のあるブラウザとは別のブラウザで開いた。…元のブラウザの端末の保存は合流しない | 保存のあるブラウザでもログインする」
- 反例の内容: 閲覧者向け機能はスマートフォン中心（T-01）。メールアプリのアプリ内ブラウザや既定のブラウザでリンクが開くと、保存のあるブラウザではログインが成立せず、閲覧者はログインをもう一度行う。「ログイン後に元の操作へ戻る」（共通の規則）も、始めたブラウザでは成立しない
- 代案: ログイン用のメールにワンタイムのコードを併せて載せ、メールアドレスを入力したブラウザでコードを入力してログインを成立させる。リンクを開く道も残す。ログインは常に始めたブラウザで成立し、KEP-04 の上の異常系とやり直しがなくなる。V-51（パスワードを使わない）を満たす

### 5-2 再申請で前の申請の内容を入力し直す

- 引用（`scenario/application.md` APP-04 手順3）: 「前の申請の内容は引き継がれない」。APP-02 異常系: 「再提出した後で、修正をやり直したい | 確認中の申請は修正できない。取り下げて（APP-03）、再申請する（APP-04）」。`pages/index.md` 申請を提出する画面の状態: 「再申請は、前の申請の内容を引き継がない」
- 反例の内容: 否認の理由に応じて一部を直す再申請（P-74）と、1か所を直すための取り下げと再申請で、利用者は店舗の情報・写真・店舗との関係などをすべて入力し直す
- 代案: 再申請は、MY-05 の否認・取り下げの申請から、その内容が入った状態で RQ の入力を始める。RQ は「再提出」で同じ始まり方をすでに持つ（差し戻された申請の内容が入った状態で始まる）ため、画面の状態は増えない。新しい申請になる点（元の申請は否認・取り下げのまま残る）は変わらない

### 5-3 引き継ぎで、後任の承諾を待ってから手放す

- 引用（`scenario/membership.md` MEM-04）: 「管理を引き継ぐ管理者は、後任を招待し（MEM-02）、後任が承諾して管理者の一覧に加わったことを確かめてから（MEM-01）、自分の権限を手放す」。ACC-04 手順3: 「退会をやめて後任を招待し（MEM-02）、後任が承諾した後に退会へ戻る」
- 反例の内容: 引き継ぎは、招待 → 後任の承諾を待つ → 一覧を確かめる → 手放す、の4段になり、退会では退会の中断と再開が加わる。待つ間に前任が手放すと、対象は管理者不在になり招待も無効になる（2-1）
- 代案: 管理者不在になっても承諾前の招待を有効のまま残す。引き継ぎは契約 B-29 のとおり「招待 → 手放す」で終わり、後任は後から承諾して管理者になる。MEM-03・MEM-04・MEM-05・ACC-04 から「招待が無効になる」の表示と異常系が消える。招待の取り消しは、管理者不在の間はサービス運営者が CM-02 で行う（代行の一般則に収まる）

### 5-4 保存一覧で誤って解除した保存を戻す

- 引用（`scenario/keep.md` KEP-02 異常系）: 「保存一覧で誤って解除した | 検索などで対象を探し、詳細から保存し直す」。KEP-03 異常系: 「閲覧できない保存を誤って解除した。対象を開けないため、保存し直せない」
- 反例の内容: 詳細では「同じ場面でもう一度操作して元に戻す」（KEP-01）のに、保存一覧では対象を探し直す操作が要り、閲覧できない保存は戻せない
- 代案: 保存一覧で解除した対象は、一覧を開き直すまで解除済みとして行に残し、同じ行で保存し直せる。取り消しは1操作になり、KEP-03 の「保存し直せない」がなくなる。VW-10 の状態が1つ増えるだけで、画面は増えない

### 5-5 位置情報もエリアもない閲覧者に、マップが何も表示しない

- 引用（`pages/index.md` CS-03）: 「VW-04 はエリアも選択していなければ対象を表示しない。VW-05 は公開中の地域を新しい順に表示する」。地図: 「VW-04 の初めの範囲は、エリアを選択中なら選択エリアの全体、選択がなく位置情報の利用を許可していれば現在地の周辺とする」。`scenario/explore.md` EXP-01 手順5: 「閲覧者が地図を動かし、別の範囲の店舗と地域を探す」
- 反例の内容: 位置情報を許可しない閲覧者は、VW-02 で都道府県・市区町村・町域をたどって適用するまで、マップで何も見られない。同じ状態で VW-01 と VW-05 は表示を続ける。初めの範囲が定義されていない
- 代案: 位置情報もエリアもない場合の初めの範囲を、公開中の店舗が収まる広い範囲（ピンはまとめて件数を示す）とし、位置情報未許可であることを併せて示す。閲覧者は地図を動かすだけで探せる。エリアの選択（V-18）は残る

## 条件6 アーキテクチャ制約に従い、アダプターを差し替えられる

### 6-1 Media と、写真を持つドメインの間の循環

- 制約: 「ドメイン間の非循環: ドメイン間に循環依存を作らない」
- 引用（`domains/index.md` 依存方向）: 「依存は型の参照を指す」「Media ← Place, Listing, Region, Event, Article, Application」「Place, Listing, Region, Event, Article のイベント型 ← Media（写真の削除の消費者）」「循環はない」
- 違反: 文書自身の定義（型の参照）で、Place・Listing・Region・Event・Article は Media に依存し、Media はそれらのイベント型に依存する。Place → Media → Place の循環になる。「（Media はイベント型だけを参照する）」は、イベント型の参照を依存に数える Application・Notification の行と扱いが食い違う。`PhotoId` は共有カーネルにあり、写真を持つドメインが Media のどの型を参照するのかは書かれていない

## 条件7 次の改訂が前より高くつかない設計である

### 7-1 申請の失効が、場合の列挙で成り立っている

- 引用（`scenario/application.md` APP-05 の表、契約 P-77 a〜g）と、各カテゴリーに散った失効の記述（SHP-10 手順5、LST-16 手順3、REG-09 手順3、REG-10 手順5、EVT-04・EVT-11、MEM-03 手順5）。`domains/index.md` は失効を「Authority, Place, Listing, Region, Event のイベント型」の消費として組む
- 列挙の漏れが 3-1（別の離脱申請の承認による解除）に出ている
- 代案: 申請の種類ごとに「前提」を1つ定義する（例: 離脱の申請の前提は「その所属がある」、管理者のいない店舗への申請の前提は「店舗管理者がいない」、参加の申請の前提は「イベントが開催前・開催中」）。失効は「確認中・差し戻し中の申請の前提が成り立たなくなった」の1規則になり、承認のユースケースも同じ前提を確かめる。P-77 の7つはこの規則の例になる
- 想定する次の要求: 申請の種類の追加（契約 X-01 の「読みもの掲載候補の受付」）。今の構造では失効の場合を列挙に足し、消費するイベント型を足す。代案では新しい種類の前提を1つ書く

### 7-2 表示範囲の規則が、複数の場所に画面の列挙で書かれている

- 引用: `scenario/explore.md` 共通の規則の表、`scenario/discover.md` DIS-01 の表、`scenario/shop.md` SHP-07 手順2、`scenario/listing.md` LST-08 手順2、`scenario/event.md` 共通の規則と EVT-11 手順2、`pages/index.md` 公開中の対象の状態（閲覧側）の表。同じ P-87 の規則を、それぞれ場面の列挙で書いている。列挙は場所ごとに違う（explore.md の表の「提供開始前・提供終了の掲載」の行にはキーワード検索と保存一覧がなく、LST-08 にはある）
- 代案: 場面を「発見の場面」と「参照の場面」の2種に分け、規則を1か所に書く（B-46 の区分）。発見の場面は、提供開始前・提供終了の掲載、閉店した店舗とその掲載、終了・中止したイベントを表示しない。参照の場面は状態を区別して表示する。pages は画面の区分ごとにどちらの場面かだけを宣言する。pages の表の3行（掲載・店舗・イベント）は、この2分で同じ切り口に割れる（VW-01・VW-04・VW-05・VW-06・VW-07・DT-03 の店舗と掲載・DT-01 の他の掲載・DT-01〜DT-03 の関連するイベントが発見、VW-03・VW-08・VW-10・DT-02 の掲載・DT-04 の参加店舗・DT-05 の紹介先・RQ-02・CF-02 が参照）。Discovery の `VisibilityPolicy` も場面の種類を引数に取れる
- 想定する次の要求: 一覧の追加（X-01 の「日付による絞り込み」の結果など）。今は6か所の列挙を直す。代案では新しい区分の種類を1つ宣言する

### 7-3 提供期間と開催日の両方を持つ状態に、操作で到達できる

- 引用（`scenario/listing.md` LST-03 異常系）: 「提供期間と開催日の両方を設定して保存しようとした。保存できない | どちらか一方を外して保存する」。LST-12・LST-13 の異常系にも同じ行がある。手順5: 「切り替えるときは、設定済みの一方を外してから他方を設定する」。手順1は「提供期間を設定するか、開催日を登録するか、どちらも設定しないかを選ぶ」
- 代案: 提供の設定を「設定しない / 提供期間 / 開催日」の排他的な1つの選択にする（ドメインでは直和型）。選択を切り替えると他方は持てないため、「両方を設定して保存」の異常系が3か所から消え、手順5の「外してから」の操作も消える
- 想定する次の要求: 提供の種類の追加（曜日の指定など）。今は組み合わせの禁止を異常系に足す。代案では選択肢を1つ足す

### 7-4 日付で決まる状態の記録を、集約が持つ

- 引用（`domains/index.md` 日付と位置）: 「日付で決まる状態（掲載の提供状態、イベントの開催の状態）は、保存せず、`LocalDate` を引数に取る純粋な関数で求める」
- 引用（同 日付で決まる状態の出来事）: 「日次のジョブが、集約に記録された『最後に確かめた状態』と今日の状態を比べ、違えば記録を更新してイベントを出す。Listing と Event がこの振る舞いを持つ」
- 反例の内容: Listing と Event の集約が、内容と、通知のためのジョブの記録の2つの責務を持つ。ジョブの書き込みは集約の版を進めるため、同じ時に編集していた店舗管理者の保存が `ConflictError` になり、CS-07「他の人が先に保存」が示される
- 代案: 「最後に確かめた状態」を、集約の外の記録（対象の ID と状態の組）としてジョブが持つ。集約は日付から状態を求める関数だけを持ち、「保存せず」と一致する。ジョブの書き込みは集約の版に触れない
- 想定する次の要求: 日付で起きる出来事の追加（提供開始の通知など）。今は集約の記録と振る舞いを足す。代案ではジョブの記録の種類を足す

### 7-5 店名・住所で店舗を探す規則が、2つのポートに分かれる

- 引用（`domains/index.md` 読み取り）: 「閲覧者に見せる読み取り（…既存店舗の確認…）は Discovery のポートが提供する」「管理側の読み取り（…サービス運営者が非公開を含めて探す読み取り）は、各ドメインのリポジトリの問い合わせが提供する」
- 引用（`scenario/shop.md` SHP-09 手順3）: 「名称・所在地が近い既存の店舗が、非公開の店舗を含めて示される」。SHP-02 と SHP-12 手順1も店名・住所で探す
- 反例の内容: 重複を防ぐための同じ照合（店名・住所の一致の規則）が、Discovery（SHP-02。公開中だけ）と Place のリポジトリ（SHP-09、SHP-12。非公開を含む）に別々に定義される。一方だけを直すと、申請者には「ない」と見えた店舗が、照合では「ある」と判断される差が広がる
- 代案: 店名・住所の照合を1つの問い合わせにし、非公開を含めるかどうかを引数にする。SHP-02・SHP-09・SHP-12 が同じ問い合わせを使う
- 想定する次の要求: 照合の規則の変更（X-01 の「重複店舗の統合」に伴う表記ゆれの吸収など）。今は2つのポートと2組の適合テストを直す
