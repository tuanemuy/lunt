# usecases / testcases の委譲ブリーフ

リポジトリは `/Users/hikaru/github.com/tuanemuy/lunt`。最初にルートの `AGENTS.md` を読む（このリポジトリの CLAUDE.md に当たる）。

担当ドメインについて、次の3つを順に書く。

1. `spec/usecases/${domain}.md` — ユースケース
2. `spec/testcases/${domain}/${usecase}.md` — ユースケーステスト（ユースケースごとに1ファイル。ファイル名はユースケース名の小文字始まり camelCase）
3. `spec/testcases/ports/${port}.md` — ポート適合テスト（担当ドメインのポートごとに1ファイル。ファイル名はポート名の小文字始まり camelCase）

## 読むもの

1. `spec/domains/index.md` — 境界、依存方向、共有カーネル、ドメインをまたぐ規約（UnitOfWork、リポジトリの共通の契約、操作の可否、申請の前提、写真の持ち主 など）。**これが正**
2. `spec/domains/${domain}.md` — 担当ドメイン。末尾の「ユースケース（概要）」が、書くユースケースの一覧。ユースケースが呼ぶ他ドメインの振る舞い・ポートは、そのドメインのファイルで定義を確かめる
3. 担当ドメインに関わる `spec/scenario/*.md`（`index.md` の共通の規則を含む）と `spec/pages/*.md` — 上流。ユースケースは pages の操作を実現する
4. `spec/review/contract.md` — 契約。AC（体験の確認基準）の関連要件の表がある
5. `docs/backend_implementation_example.md` の Usecase の節、`docs/test.md` — テンプレートのユースケースとテストの形

## 層の決まり

| 層 | 上流 | 決め切る | 書かない |
| --- | --- | --- | --- |
| `spec/usecases/` | pages の操作 / domains | 使うドメインの振る舞いとポート、トランザクション境界、要求が振る舞いを定めるエラー | DTO の全フィールド、処理手順の番号付き記述、技術的に起こりうるだけのエラー |
| `spec/testcases/${domain}/` | usecases / domains の不変条件 / flows の失敗時の扱い | 要求が満たされたと言える代表ケース | 境界値、入力バリデーションの組み合わせ、技術的なエッジケース |
| `spec/testcases/ports/` | domains のポート契約 | 契約の全項目 | バックエンドに依存するケース |

### ユースケースの形式（`usecase-guide.md` の転記）

ファイルの冒頭にドメイン名とユースケースの一覧（名前、一行の説明、実現するシナリオ ID・画面 ID）。各ユースケースは次の節を持つ。

- `## ユースケース名`（ドメインの言葉で命名。〜Page などの画面の語彙を使わない。1画面のデータ一式 ≠ 1ユースケース。複数の読み取りを1つに合成してよいのは、合成をまたぐ規則があるときだけ）
- `### 概要`
- `### 入出力` — 何を受け取り何を返すかが伝わる粒度まで。全フィールドの列挙はしない。要件が定めるバリデーションがあれば添える。操作する人（`Actor`）を取るかどうかを書く
- `### 使用するドメインの振る舞い・ポート` — 呼び出すドメインの振る舞いとポートメソッドを列挙する。手順の番号付き記述はしない。ここに書いた名前は、domains のファイルに定義がなければならない。定義が無い・食い違う場合は、usecases に書いて済ませず、返答で伝える
- `### トランザクション境界` — UnitOfWork の要否。必要なら、スコープに含まれる書き込み、スコープ内で使うリポジトリ、ロールバックが起きる条件。不要なら理由を一行。複数の書き込みを原子的に確定しない場合は、途中失敗時に残る状態
- `### エラーケース` — 要件・シナリオが振る舞いを定めるエラーだけ（条件と種類）。権限なし、前提の変化、競合、閲覧できない対象、入力エラーのうちシナリオの異常系にあるもの

ドメインイベントの消費者と日次のジョブも、ユースケースとして同じ形式で書く（入力はドメインイベントまたはスケジュール。冪等であることと、その守り方を概要に書く）。

### ユースケーステストの形式（`testcase-guide.md` の転記）

```markdown
# {ユースケース名}

| 前提条件 | 操作 | 期待結果 | 実装ステータス |
|---|---|---|---|
| テストの前提状態 | 実行する操作 | 期待される振る舞い | |
```

- 正常系（基本フロー）、要件由来の異常系（ユースケースに列挙したエラーケースとシナリオの代替フロー）、不変条件（破る操作を拒否すること）
- 期待結果は spec の記述から一意に決まること（返す内容、保存される状態、出るドメインイベント、エラーの種類）
- 境界値・技術的なエッジケース・入力バリデーションの組み合わせは書かない
- 実装ステータスの列は空欄
- 契約の AC のうち担当ドメインのユースケースで確認できるものは、該当するケースの前提条件か期待結果の末尾に `（AC-xx）` と添える。担当ドメインに関連要件を持つ AC が、どれかのケースに添えられていること

### ポート適合テストの形式

同じテーブル形式。ポートの契約の全項目を網羅する。

- メソッドの基本動作（正常系と、契約に書かれたエラーケース）
- 一意性・整合性（ポートが担保するとした制約が、違反時のエラーを返すか）
- クエリ要件（絞り込み・並び順・ページング・件数上限。0件、1件、上限ちょうど、上限超過、範囲の外の page を含む）
- 並行性（楽観ロックの競合で契約どおりのエラー）
- 可視性（read-your-writes）
- UnitOfWork の中での振る舞い（コミットで反映、ロールバックで1件も残らない）。UnitOfWork ポート自体の適合テスト `spec/testcases/ports/unitOfWork.md` は別の担当が書くので、書かない
- 永続化技術に依存する記述を書かない。前提条件は対象ポートのメソッド呼び出しだけで組み立てる。in-memory と PostgreSQL の片方でだけ通るケースを作らない。検証不能なケースが出たら契約が曖昧な兆候なので、返答で伝える
- 外部サービスのポート（メール送信、写真の保存先、外部アカウントの検証など）は、契約に書かれた振る舞いを、テスト用の実装と本番の実装が共通で通す形で書く

## 共通の決まり

- 契約と上流にない要素を足さない。上流から決まらない判断が必要になったら、補完せず返答の「未決の問い」に挙げる
- 現在形で書く。経緯・代替案・検討の過程は書かない
- ユースケースの名前と入出力に画面の語彙（画面 ID、〜画面、タブなど）を使わない。シナリオ ID・画面 ID は、一覧の「実現する」列にだけ書く
- ビジネスルールをユースケースに書かない。ルールはドメインの振る舞いにあり、ユースケースは事実を読んで渡し、結果を保存する
- 担当外のファイルは変更しない。domains のファイルの誤り・不足は、直さず返答で伝える

## 返答

成果物はファイルに書き、返答は要約だけにする。

- 書いたファイルの数（usecases、ユースケーステスト、ポート適合テスト）
- 未決の問い（なければ「なし」）
- domains のファイルへの指摘（定義の無い振る舞い・ポート、食い違い。なければ「なし」）
- 動的フロー（複数のユースケース・時間をまたぐもの）として flows に載せるべきものの一覧（名前と、関わるユースケース）
- 散文は5行以内。ファイルの読み取りは Read / Grep ツールを使う
