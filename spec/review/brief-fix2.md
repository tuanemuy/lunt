# 独立した読みの反例の直しの委譲ブリーフ

リポジトリは `/Users/hikaru/github.com/tuanemuy/lunt`。最初にルートの `AGENTS.md` を読む。

spec（`spec/index.md` が全成果物へのリンクを持つ）に対して、独立した読み手が完了の定義の 7 条件への反例を `spec/review/read-*.md` に挙げた。依頼文が示す読みのファイルの反例を、担当の範囲で直す。

## 読むもの

1. 依頼文が示す `spec/review/read-*.md` — 反例の一覧（条件ごと。引用つき）
2. `spec/review/criteria.md` — 7 条件と層の表、アーキテクチャ制約
3. `spec/review/contract.md` — 契約（要求の台帳と解釈）。上流の正
4. 反例が引用するファイルと、その上流・下流のファイル。技術設計は `spec/domains/index.md` が規約の正

## 直し方

- **7 条件への反例は、どれも見送らない。** すべて直す。「7 条件の外」の指摘は、直すと明らかに良くなり、契約に反しないものだけ直す（見送ったものは返答に挙げる）
- 上流が正。下流の記述は上流から決まる。反例が上流の誤り・不足を示しているなら、上流を直し、下流へ伝播し直す（scenario → pages → domains → usecases → flows → testcases）。担当の範囲の外のファイルに直しが要る場合は、直さず返答で伝える（依頼文が範囲を示す）
- 条件 5・7 の反例は、読み手の代案を採る。代案が契約に反する、または別の条件の反例を生む場合だけ、別の直し方を選び、理由を返答に書く
- 条件 3 の反例（決まっていない問い）は、契約と上流から一意に決まるならそのとおりに決める。決まらないなら、既存の規則（例外を作らない、同じルールを2か所に書かない）に最も沿う答えを選んで書き、何を選んだかを返答に書く
- 同じ規則は1か所に書き、他は参照にする。直しで規則の重複を増やさない
- 現在形で書く。経緯・代替案・「変更した」「以前は」などは書かない。契約にない要求を足さない
- 直した後、直した記述を参照している他の箇所（同じ層の他のファイル、下流）を Grep で探し、食い違いが残らないようにする

## 返答

要約だけ。

- 反例ごとに、直した（ファイル）か、範囲の外で直せなかったか
- 自分で答えを選んだ点（条件 3、代案を採らなかった点）
- 範囲の外のファイルに要る直し
- 散文は10行以内。ファイルの読み取りは Read / Grep ツールを使う

## 再委譲の注意

前の実行が利用上限で途中で中断している。担当の範囲のファイルは、一部だけ直っている可能性がある。spec のファイルは git に未コミットなので `git diff` では差分が見えない。次のとおり進める。

- 反例ごとに、引用された箇所の現在の内容を読んで、直っているかどうかを確かめる。直っているものはやり直さず、残りを直す
- 改名の途中に注意する（新旧2つの名前のファイルが並んでいる、片方だけ直った参照、`spec/index.md` のリンク）。Grep で旧名の残りを探す
- `spec/review/decisions-read1.md` は前の実行の後に追記されている。全文を読み直す
