# 独立した読み 1: scenario

区分は `spec/scenario/`（index.md と13カテゴリーの全文）。上流は `spec/review/contract.md`。区分の外は、区分の中の記述が指す定義を確かめる範囲で `spec/pages/`、`spec/domains/`、`spec/usecases/`、`spec/flows/`、`spec/requirements.md` を部分的に読んだ。

反例の件数: 条件1は1件、条件2は2件、条件3は0件、条件4は4件、条件5は0件、条件7は1件。7条件の外は5件。条件6は scenario に問わない。

## 条件1 要求を取りこぼしていない

### 1-1 LST-15・LST-16 に権限不足の異常系がない

- 契約の引用: M-25「サービス運営者は管理者のいない店舗の掲載を代理で作成・公開できる」、M-35「管理者のいない店舗の掲載はサービス運営者が更新・一時非公開・提供終了・削除する」
- scenario の引用: `listing.md` 共通の規則「店舗管理者が操作できるのは、管理権限を持つ店舗の掲載だけ。権限のない店舗の掲載には操作の入口が示されず、直接たどり着いても操作できないことが示される」
- 反例: 観点は権限不足。listing.md の共通の規則が定めるのは店舗管理者の権限だけで、サービス運営者でない利用者（役割を解除された利用者を含む）が管理者のいない店舗の代理作成（LST-15）と掲載の管理（LST-16）にたどり着いたときの、利用者の次の操作が決まっていない。LST-15 の異常系は「店舗管理者のいる店舗である」、LST-16 は「その店舗に店舗管理者が就いた」だけを持つ。同じ代行の操作である SHP-12・SHP-13 は「サービス運営者でない利用者がたどり着いた」の行を持ち、`moderation.md`・`operation.md` は共通の規則で定める。listing.md にはどちらもない

## 条件2 足しすぎていない

### 2-1 運営による非公開の掲載は複製できない、の引用元がない

- 引用: `listing.md` LST-09 異常系「運営による非公開の掲載を複製しようとした。複製の入口は示されず、複製できない」。同じ規則が LST-09 手順1「下書き・公開・一時非公開のどの掲載も…複製できる」、LST-11 手順3「公開状態は変えられず、複製もできない」、`moderation.md` MOD-07 手順4「店舗管理者は掲載を削除できるが、複製はできない」にある
- 反例: 上流に引用元がない。M-22 は「掲載を複製して作成できる」、M-43 は「閲覧できず、店舗管理者は再公開できない。サービス運営者だけが解除できる」、I-15 は「公開状態を変更できず…情報の更新はできる」で、複製の禁止を定めない。同じ規則は運営による非公開の掲載の編集を認めているため、店舗管理者は LST-01 で同じ内容の掲載を作れ、禁止は何も防がない
- 代案（条件7にも当たる）: 複製は公開状態を問わず認める。運営による非公開の規則は「公開状態の変更だけを止める」の1文になり、「編集と削除はできるが、複製はできない」という操作ごとの列挙が消える

### 2-2 地図のピンのまとめ方を scenario が書いている

- 引用: `explore.md` EXP-01 手順2「公開中の店舗が収まる範囲が、近くの店舗をまとめて件数を示した状態で表示され」
- 反例: 層の表の「書かない」（UI パターン）に当たる。契約 D-09 は「地図: 移動に応じた再検索、ピンの集約」を「画面設計で扱う事項を pages が定める」とし、`pages/index.md`「地図」が同じ内容（「ピンをまとめて件数を示した状態で表示し」）を持つ。scenario が決めるのは初めの範囲までで足りる

## 条件3 Issue をまたぐ決定が決まりきっている

反例なし。scenario が値を持たない事柄（周辺の範囲、開催日の順の向き、連続しない規則が成り立たないときの並び、代行の期間）は、下流（`domains/discovery.md`、設定値）に一意の答えがある。

## 条件4 矛盾がなく、現在形で単体で読める

### 4-1 現在地の利用を始める場面が食い違う

- 引用1: `discover.md` DIS-06 手順1「閲覧者がフィードで現在地の利用を始める」
- 引用2: `explore.md` EXP-01 異常系「または位置情報の利用を許可する（DIS-06）」、EXP-03 異常系「または位置情報の利用を許可する（DIS-06）」
- 引用3: `pages/browse.md` VW-04 機能「現在地の利用を始める。許可すると、現在地の周辺を示す」、VW-05 状態「現在地の利用を始めて許可する」。`pages/index.md` は DIS-06 を VW-01・VW-04・VW-05 に割り当てる
- 反例: DIS-06 はフィードだけを開始の場面にするが、EXP-01・EXP-03 は地図・地域の一覧から DIS-06 へ送り、pages は地図と地域の一覧でも始められると定める。scenario の文面どおりなら、地図で位置情報未許可の閲覧者はフィードへ移って許可し、地図へ戻ることになり、条件5の迂回にも当たる。DIS-06 の手順1を「フィード、地図、地域の一覧のいずれかで」にすれば両方が消える

### 4-2 地域の詳細から開いた地図の範囲と条件の効き方が、EXP-01 と pages で食い違う

- 引用1: `explore.md` EXP-01 手順2「エリアを選択中は選択エリアが、選択がなく位置情報の利用を許可していれば現在地の周辺が表示される。どちらもなければ、公開中の店舗が収まる範囲が…」、手順4「エリアを選択中は、所在地が選択エリアにある店舗と…地域に限られる」
- 引用2: `explore.md` EXP-04 手順8「閲覧者は、地域の位置と所属する店舗の位置を地図で確認できる（EXP-01）」
- 引用3: `pages/index.md`「地図」「DT-03 から開いたときは、その地域の位置と所属する店舗の位置が収まる範囲とし、その地域を選んだ状態にする」「地域を選んでいる間…その地域の概要と所属する店舗の位置の表示には、選択中のエリア・カテゴリーの条件は効かない」。`pages/browse.md` VW-04 は「条件の効き方は EXP-01 が定める」と述べる
- 反例: EXP-01 は初めの範囲を3通りで言い切り、条件は常に効くとする。EXP-04 から進んだ場合の範囲と、地域を選んでいる間に条件が効かないことは EXP-01 になく、pages と `usecases/discovery.md` の `findInitialMapExtent` が上流にない振る舞いを定めている。EXP-01 の文面どおりなら、エリアを選択中の閲覧者は地域の詳細から地図を開いても選択エリアが表示され、V-50「広がりは所属店舗の位置で確認できる」を満たせない

### 4-3 入力の途中の選択の候補の表示範囲が、index.md と event.md で食い違う

- 引用1: `scenario/index.md`「表示範囲」の参照の場面「提供開始前・提供終了の掲載、閉店した店舗とその掲載、終了・中止したイベントを、状態を区別して表示する」、当たる場面に「入力の途中の対象の選択の候補」
- 引用2: `event.md` EVT-01 異常系「下書き・一時非公開・運営による非公開の掲載と、提供終了の掲載は、添える対象に示されない」、手順2「参加するイベントを、開催前・開催中のイベントから探して選ぶ」。EVT-02・EVT-10 の異常系も同じ
- 反例: index.md は、選択の候補に提供終了の掲載と終了・中止したイベントを状態を区別して表示すると定め、event.md は示さないと定める。`editorial.md` EDT-02 は index.md のとおり（提供終了・閉店・終了も候補に示す）。`pages/index.md` CF-02 は「候補の範囲は呼び出す画面が定める」と読み替えて解消しているが、scenario にその区別（候補の範囲は各シナリオが定め、範囲に入る対象を参照の場面として示す）がない

### 4-4 scenario が引用する契約の ID の定義が、spec から辿れない

- 引用: 各シナリオの「契約:」の行（例: `discover.md` DIS-01「P-30、P-61、B-01、B-07、D-01、I-07、UC-01」）。`moderation.md` 共通の規則「通知の出来事は P-91〜P-100 が正」
- 反例: P-・I-・D-・X- の ID は `spec/review/contract.md` だけが定義する。`spec/requirements.md`・`spec/design-appendix.md`・`spec/idea.md` にこれらの ID はなく、`spec/index.md` は `review/` のどのファイルにもリンクしない。scenario はこれらの ID を約980か所で引用し、moderation.md は規則の正を P-91〜P-100 に委ねている。定義のない参照に当たる。契約を spec の一部として `spec/index.md` の出典に載せるか、ID を REQ・APX の節へ置き換えると解消する

## 条件5 利用者の目的が迂回なく達成できる

反例なし。UC-01〜UC-15 と運営・編集の各シナリオについて、入口を減らす案（イベントの詳細から参加申請を始める、地域の登録と公開を1操作にする、連絡への対応で店舗管理者を一括で解除する、公開前の確認を経ずに公開する）を比べたが、契約の定め（B-04、I-03、D-03、D-07）か操作の追加が上回り、代案のほうが良いものはなかった。DIS-06 の迂回は 4-1 に含めた。

## 条件7 次の改訂が前より高くつかない

### 7-1 カテゴリーをまたぐ共通の規則が、カテゴリーごとに別々に定義されている

- 引用（所在地の入力）: `shop.md` 共通の規則「所在地は、郵便番号、または都道府県・市区町村・町域の階層から町域を選んで決め…町域に対応しない郵便番号（事業所固有の郵便番号を含む）では町域の候補が出ない」、`region.md` 共通の規則「地域の所在地は、郵便番号、または…町域を選んで決める」と REG-06・REG-12 の異常系「所在地に入力した郵便番号が町域に対応しない…」、`event.md` 共通の規則「イベントの開催場所の所在地は…」と EVT-04・EVT-12 の同じ異常系
- 引用（写真の同意）: `shop.md`・`listing.md`・`region.md`・`event.md`・`editorial.md` の共通の規則がそれぞれ「写真を登録する操作のたびに…同意」を定義し、SHP-03・SHP-06・SHP-08・SHP-12・SHP-13・LST-02・REG-06・REG-12・EVT-04・EVT-12・EDT-01・EDT-04 が同じ異常系を持つ
- 引用（運営による非公開の間にできる操作）: `listing.md`・`region.md`・`event.md`・`moderation.md` の共通の規則がそれぞれ定義する
- 引用（不在の対象への通知の宛先）: `account.md` ACC-03、`membership.md`、`region.md`、`event.md`、`moderation.md` の共通の規則がそれぞれ定義する
- 反例: 同じルールが2か所以上に別々に定義されている。いまは文面が一致しているが、次の要求（例: 事業所固有の郵便番号を受け付ける、写真の同意に項目を足す）で 3〜5 ファイルと最大12の異常系の行を同じ向きに直すことになる
- 代案: `scenario/index.md` の「共通の規則」に、「表示範囲」「申請の前提」と同じ形で「所在地の入力」「写真の登録と同意」「運営による非公開」「不在の対象への通知」を1つずつ置き、各カテゴリーは参照だけを持つ。入力エラーの行は index.md の規則の1行に集まる。pages は同じ事柄をすでに共通機能（`pages/index.md` CF-07 ほか）に集めており、scenario だけが分散している

## 7条件の外

- `listing.md` LST-07 は、一時非公開で起きること（手順2）に編集担当者への通知を書いていない。LST-08 手順3、LST-10 手順4、REG-07 手順4、EVT-06 手順4 は書いている。通知そのものは EDT-06 手順1「非公開、公開の取り下げ、削除」と `flows/index.md`（`listing.unpublished`）が持つ
- `application.md` APP-05 の表の例「直接の追加で参加がすでに成立した」は起こらない。参加の申請は店舗管理者がいることを前提にし、直接の追加は店舗管理者のいない店舗に限られる（E-11）。店舗管理者が不在になった時点で申請は別の前提で失効している。index.md の参加の前提「その店舗の参加がまだない」は、承認時の確認としてだけ働く
- `listing.md` LST-04 は、公開前の確認が公開の必須の手順かどうかを述べていない。EDT-03 手順2 は「確認は公開の必須手順ではなく」、LST-12 手順4 は「確認は必須ではなく」と述べる。`pages/shop.md` は SM-04 から公開できるとして決めている
- `listing.md` LST-12・LST-13 の前提「ログインしている」は、手順1（SHP-02 での確認、店舗詳細からの開始はログイン不要）と合わない。REG-03 は同じ状況を手順1の中のログインへの案内で書いている
- 区分の外: `domains/listing.md`（`duplicate` の行「decisions-scenario L-3」）と `domains/discovery.md`（「decisions-scenario D-3」）が `spec/review/` の作業メモを引用している。条件4の「定義のない参照」の候補で、domains の読み手の区分
