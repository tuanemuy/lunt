# 完了の定義と層の表（転記）

## 完了の定義

Implementation Ready とは、実装者が設計を判断し直さずにコードを書ける spec のこと。次の 7 つが成り立ち、それぞれを根拠で示せる。

spec が持つのは、複数の Issue にまたがって効く決定（用語・ドメインと境界・ビジネスルール・ポートの契約・シナリオ・画面構成）。ここがぶれると実装が Issue ごとに食い違う。1 つの Issue の中で閉じる詳細は、issue-planner が実装時にコードを読んで決める（`../../issue-planner/SKILL.md`）。spec に先取りして書いても、実装で決め直す。

成り立つとは反例が無いこと。反例は条件ごとに決まった形を取り、spec か契約の記述の引用を伴う。設計ドキュメントには足す方向の指摘がいくらでも出せるため、引用のない指摘を反例に数えると、反例ゼロは書き尽くした状態でしか成立しない。形を取らない指摘は 7 条件の外の指摘として扱う。

7 つは同じ硬さで扱う。その時点の spec に対して、読み手が 7 つへの反例ゼロと返している spec だけが Implementation Ready。

5 は体験設計の層（scenario / pages）、6 は技術設計の層（domains / usecases / flows / testcases）が範囲にあるときだけ問う。

### 1. 要求を取りこぼしていない

- 契約の各項目が、範囲の最上流の層から最下流の層まで辿れる
- 各層は、層の表が定める上流に書かれた事柄を落としていない
- scenario は、契約が定める異常系に加え、4 観点（入力エラー・権限不足・リソース不在・操作の取り消し）の異常系を持つ

反例の形: 上流の記述の引用と、それが落ちていない下流の場所。scenario の 4 観点では、契約の項目の引用と、どの観点で利用者の次の操作が決まっていないか。4 観点の外の異常系は、契約に引用元があるときだけ反例になる

根拠: 契約の項目ごとの辿り先

### 2. 足しすぎていない

- すべての要素が上流の記述に辿れる
- 層の表の「書かない」に当たる記述がない

反例の形: その記述の引用と、上流に引用元がないこと、または「書かない」のどれに当たるか

根拠: 最下流の層から上流へ逆向きに辿った結果

### 3. Issue をまたぐ決定が決まりきっている

- 層の表の「決め切る」の各項目に、spec の記述から一意に決まる答えがある
- テストケースの期待結果が spec の記述から一意に決まる
- 動的フローが閉じている
  - すべての状態に入る遷移があり、出る遷移か終端の明示がある
  - 各遷移に実行主体（ユースケース / ジョブ / トリガー）がある
  - イベントに消費者がいて、投影・通知の更新元が揃っている
  - ファイル・外部リソースは生成・参照・削除が揃っている
  - 各状態がエンティティのライフサイクルとポートの契約で表現できる

反例の形: 答えが決まっていない問いと、その答えに依存する 2 か所（ユースケース・画面・アダプター・テストケース）。1 か所にしか効かない問いは Issue の中で決まるので反例にならない。動的フローでは、状態と、欠けている遷移・主体・消費者

根拠: 決定の種類ごとの定義場所、フローごとのトレース結果

### 4. 矛盾がなく、現在形で単体で読める

- 定義どうしが食い違っていない。同じものを指す語は 1 つ
- 下流が参照する振る舞い・ポートメソッド・画面が、上流に定義されている
- 経緯・代替案・旧仕様の記述がない

反例の形: 食い違う 2 か所の引用、定義のない参照の引用、経緯を述べる記述の引用

根拠: 用語と参照の突き合わせ結果

### 5. 体験設計がある場合は、利用者の目的が迂回なく達成でき、画面の役割が重ならない

- 各シナリオで、利用者の目的が不要なステップなしに達成できる
- 各画面の目的が一文で言え、2 つの画面が同じ役割を負っていない

反例の形: 同じ目的をより少ないステップ・画面で達成する代案

根拠: シナリオごとに比べた代案

### 6. 技術設計がある場合は、アーキテクチャ制約に従い、アダプターを差し替えられる

- `../../spec-domain/SKILL.md` の「アーキテクチャ制約」に違反していない
- ポートが永続化技術の語彙・型（テーブル名・カラム名・SQL 片・ORM の型）を露出していない
- 一意性・参照整合性をポートと呼び出し側のどちらが担保するかが、全メソッドで決まっている
- 書き込みを持つユースケースに、必要な原子性とその保証方法が書かれている
- ユースケースの名前と入出力に画面の語彙がない
- ポート適合テストが特定のバックエンドを前提にしていない

反例の形: 制約と違反箇所の引用、または in-memory と PostgreSQL の片方でだけ通るケース

根拠: 制約ごとの確認結果

### 7. 次の改訂が前より高くつかない設計である

制約への準拠は 6 が見る。7 が見るのは、この spec に次の要求が来たとき、改訂が前より広がらないか。

- 1 つのエンティティ・ユースケース・画面が 2 つの責務を負っていない
- 例外の列挙で成り立っているルールがない
- あり得ない状態の組み合わせを型で排除している（排他的な状態は直和型）
- 同じルールが 2 か所に別々に定義されていない

反例の形: 曖昧な分岐や例外が消える代案の構造

根拠: 次に来そうな要求を 1 つ想定して、その改訂がどの層のどこまで広がるかを述べられること

## 層

条件 1〜3 は、層ごとの上流・下限・上限をこの表から取る。

| 層 | 上流 | 決め切る | 書かない |
| --- | --- | --- | --- |
| `spec/scenario/` | 契約 | 利用者の操作とフロー、異常系 | UI パターン（タブ・モーダル等） |
| `spec/pages/` | scenario | 画面・目的・機能・状態と遷移のきっかけ | 条件の組み合わせを展開した個別ケース、データ項目の型・制約、メッセージの文面 |
| `spec/domains/` | scenario / pages（spec-domain では契約） | 用語、ドメインの境界と依存方向、エンティティと値オブジェクトの型・振る舞い・不変条件・ライフサイクル、ポートのシグネチャと振る舞いの契約、UnitOfWork ポート | 物理スキーマ、永続化技術の語彙 |
| `spec/usecases/` | pages の操作 / domains | 使うドメインの振る舞いとポート、トランザクション境界、要求が振る舞いを定めるエラー | DTO の全フィールド、処理手順の番号付き記述、技術的に起こりうるだけのエラー |
| `spec/flows/` | usecases | 遷移と実行主体、終端、失敗時の扱い | 単一ユースケース内で完結する処理 |
| `spec/testcases/${domain}/` | usecases / domains の不変条件 / flows の失敗時の扱い | 要求が満たされたと言える代表ケース | 境界値、入力バリデーションの組み合わせ、技術的なエッジケース |
| `spec/testcases/ports/` | domains のポート契約 | 契約の全項目 | バックエンドに依存するケース |

pages で、既に書かれた原則・共通規則から導出できる個別ケースは、規則がある時点で定義済み。

各層の成果物の形式は次のガイドが定める。

| 層 | 形式 |
| --- | --- |
| scenario | `../../spec/references/scenario-guide.md` |
| pages | `../../spec/references/pages-guide.md` |
| domains | `../../spec-domain/references/domain-guide.md` |
| usecases / flows | `../../spec-domain/references/usecase-guide.md` |
| testcases | `../../spec-domain/references/testcase-guide.md` |

## アーキテクチャ制約（条件6の基準。転記）

完了の定義の 6 が基準にする。

- **ドメインモデルの独立性**: ドメイン層はインフラ層（DB, HTTP, 外部API）に依存しない
- **ビジネスロジックの配置**: ビジネスルールはエンティティまたはドメインサービスに置く。ユースケース層はオーケストレーションのみ
- **集約境界**: 他の集約のエンティティは ID で参照する。直接の参照を持たない
- **ポートによる抽象化**: 外部依存はすべてポート（インターフェース）経由。メソッドシグネチャと振る舞いの契約まで定義する
- **アダプターの差し替え可能性**: ポートは特定の永続化技術・外部サービスに依存する語彙や型を露出しない。同じポートを in-memory / SQLite / PostgreSQL のどれで実装しても契約が成立する。**設計の成果物はテーブル定義ではなくポートの契約であり、物理スキーマは実装時にバックエンドごとに決める**
- **トランザクション境界の明示**: 原子的に確定する書き込みの範囲を明示する。集約数にかかわらず、リポジトリ単体の契約で必要な原子性を保証できない場合は `UnitOfWork` ポートを使う。単一集約への使用も許容する
- **ドメイン間の非循環**: ドメイン間に循環依存を作らない
