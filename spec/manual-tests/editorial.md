# 読みもの編集 テスト

## 概要

このドキュメントは、編集担当者が読みものを作成・編集し、紹介先を結びつけ、公開前に見え方を確かめて公開し、公開を取り下げ、紹介先の変化に応じて紹介内容を直す操作に関するマニュアルテストの手順書です。

対応シナリオ: `spec/scenario/editorial.md`

画面名・画面 ID・共通の状態（CS）・共通の機能（CF）は `spec/pages/` の用語に従う。期待結果の「CS-xx の状態」は `spec/pages/index.md` の「共通の状態」が定める内容を指す。画面に示す文面は pages が定めないため、期待結果は画面の状態・示される内容・遷移先で書く。申立てで写真が削除された読みものの再公開（MOD-03）は `moderation.md` が扱う。

テストケースの ID は追加の順に振っているため、文書の中の並びと番号の順が違う箇所がある。TC-EDT-007・TC-EDT-008 は欠番。

## 前提条件

### 環境

- テスト環境で Lunt が起動していて、PC のブラウザからアクセスできる
- テスト環境が送るメールを、宛先のメールアドレスごとに確かめられる（以下「テスト環境で受け取ったメール」）
- ドメインイベントのリレーと消費者（通知の配送）が動いている。通知とそのメールは非同期に反映されるため、手順の「MY-03 を開く」「MY-03 の通知を選ぶ」「テスト環境で受け取ったメールを確かめる」は、反映されるまで待ち、MY-03 を読み込み直してから行う
- 通知が届かないことを確かめる手順は、同じ出来事が別の宛先に届いたこと、または同じ時点の別の出来事が届いたことを先に確かめてから行う。待つだけでは、配送の前の「届いていない」と区別できない
- テスト環境の時刻を進め、戻せる。日次のジョブ（開催の状態の記録、掲載の提供終了の検知）を任意の時点で実行できる（イベントの終了と掲載の自動の提供終了の確認に使う）。日次のジョブは、手順が実行を指示したときだけ動く（テスト環境で自動の実行を止めておく）
- Cookie を共有しない3つのブラウザ（別のブラウザ、または別のプロファイル。プライベートウィンドウを使うなら3つのうち1つだけ）を使う。以下、ブラウザ A・ブラウザ B・ブラウザ C と書く。ブラウザ C は閲覧者の確認に使い、ログインしない
- ログインは MY-02 で、メールアドレスを入力し、テスト環境で受け取ったメールのコードを入力して行う
- 対象の選択（CF-02）で対象を選ぶ手順が入力する語を書かないときは、その対象の名称をキーワードに入力して探し、候補から選ぶ
- 郵便番号・町域のデータに、`110-0001`（東京都台東区谷中）、`110-0005`（東京都台東区上野）、`113-0031`（東京都文京区根津）が入っている
- テスト用の写真のファイル（JPEG）として、テストデータの写真 `target-1.jpg`・`kyujitsu-1.jpg`・`kyujitsu-2.jpg`・`akari-photo.jpg` と、手順で登録する `photo-new.jpg`・`photo-new2.jpg` を用意する。写真用のファイルは、それぞれ見た目で区別できる画像にする（例: ファイル名を画像の中に大きく描き込む）。期待結果の「`{ファイル名}`」は、写真に描き込んだ名前で確かめる
- 写真として扱えないファイル `not-photo.pdf`（PDF）を用意する
- 通信エラーの確認には、ブラウザの開発者ツールでネットワークをオフラインにする
- 「今日」は、そのテストケースを行う日を指す。事前準備1・3でテストデータを入れるときは、相対の日付を入れる日に合わせる。TC-EDT-061・TC-EDT-062 は、テストデータを入れた日のうちに行う

### 事前準備

1. 他の文書のテストデータを残さず、この文書のテストデータだけを投入した環境で始める（同じメールアドレス・名称が他の文書では別の立場・状態を持つ）。上のテストデータを、表のすべての列の値（アカウントの立場、紹介先に使う対象の名称・所在地・状態、読みものの状態・作成・タイトル・写真・本文・紹介先の順）と、表の前の段落のカテゴリー・位置・写真で投入する（掲載・店舗・地域・イベントはサービス運営者の代理登録・登録と店舗管理者の操作で、店舗管理者は管理権限の申請（RQ-03）と承認（CM-01）で、編集担当者とサービス運営者は役割の付与で、読みものは編集担当者の作成と公開・公開の取り下げ（AM-02）で作る。またはテスト環境のデータ投入で用意する）。TC-EDT-069 は、アカウントと役割を投入した後、読みものを投入する前に行う
2. 各テストケースの「前提」の準備を終えた後、手順1の前に、ブラウザ A・B・C の Cookie とサイトデータを消去し、ログインしていない状態にする（Lunt はログアウトの操作を持たない）。前提の準備が、URL を控える操作や別のテストケースの手順など複数の部分からなるときは、部分の間でも同じ消去を行う。控えた URL は消去の後も使う。手順の「{ブラウザ} で {利用者} としてログインし」は、ログインしていないそのブラウザで MY-01 のログインから MY-02 でログインすることを指す。1つのブラウザで利用者を替える「ログインし直し」は、次のどちらかで行う
   - (a) そのブラウザの Cookie とサイトデータを消去し、MY-01 のログインから、替える利用者でログインする（端末の保存も消える）
   - (b) ブラウザ C の MY-02 で替える利用者のメールアドレスを送り、テスト環境で受け取ったメールのリンクを、替えるブラウザで開く（そのブラウザのアカウントが切り替わる）
3. テストケースの「前提」がテストデータと違う状態を求めるときは、その「前提」に従って準備する。データを変えたテストケースと時刻を進めたテストケースの後は、テストデータと時刻を初期状態に戻してから次のテストケースへ進む
4. 手順の「{申立て} の OM-04 を開く」は、MY-01 のサービス運営から OM-01 を開き（すでに運営の画面にいれば省く）、その1件を開くことを指す。OM-01 は1件ごとに種類・対象・申立人だけを示すため、一覧に同じ種類・同じ対象・同じ申立人の行が複数あるときは、開いた OM-04 の内容（申立ての理由と示した写真）がそのテストケースの値であることを確かめ、違えば一覧へ戻って別の行を開く
5. 手順の「「{対象}」の OM-03 を開く」「「{対象}」の OM-03 で…する」は、MY-01 のサービス運営から OM-01 を開き（すでに運営の画面にいれば省く）、運営のナビゲーション「対象を探す」で OM-02 を開き、店舗は店舗の名称に、掲載・地域・イベントはキーワードに対象の名称を入力して探し、結果から OM-03 を開くことを指す
